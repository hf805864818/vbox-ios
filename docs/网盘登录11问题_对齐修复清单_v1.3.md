# 网盘登录 / 播放 11 问题 · 对齐 iOS 修复清单 + Windows 安装包实施方案 v1.3

> 范围：Flutter 端 Windows 实测暴露的 11 个问题（百度 / 夸克 / UC / 115 网盘登录、播放、Node 常驻系统）+ Windows 安装包（Inno Setup）动效 UI 落地实施方案。

## 1. 【P0 · A 组】Node 扫码登录护栏缺失 → 问题 2 / 7 / 9 / 10

### 1.1 现象
- 问题 2：百度 Node 扫码偶发「登录失败 · 登录任务不存在或已结束」。
- 问题 7：夸克 Node 扫码「正在生成二维码…」一直转圈。
- 问题 9：UC 切到 Node 两步登录页「正在生成二维码…」一直转圈。
- 问题 10：115 Node 登录同样「正在生成二维码…」一直转圈。
（用户判断「整个 Node 扫码登录都是这问题」——成立。）

### 1.2 根因（Flutter vs iOS）

| 环节 | iOS（正确） | Flutter（缺陷） |
|---|---|---|
| 终端态处理 | `handleTerminal()`：`terminal=true` 时 **自动重新生成二维码**，最多 `maxAutoRegen` 次，延迟 600ms（`NodeLoginViews.swift:746-762`） | `node_login_gateway.dart:146-150` 直接 `throw CloudDriveLoginException`，**无重生成** |
| 传输层语义 | `NodeLoginAPIClient.request` 识别 `terminal` 并抛 `NodeLoginError.terminal`（`NodeLoginViews.swift:41-46`） | `node_login_client.dart:95-98` 仅透传 `terminal`，抛错时丢失分类 |
| 并发/代数护栏 | `pollCtx.inFlight` + `pollCtx.generation`，1.5s 定时器配 10s 超时（`NodeLoginViews.swift:680-698`） | `login_controller.dart:318-321` 用 `Timer.periodic(2s)` 且 **无 in-flight/代数护栏**，20s 超时会请求叠压 |
| 瞬时失败容忍 | `consecutiveFailures` 计数，达上限才停（`NodeLoginViews.swift:734-736`） | `login_controller.dart:153-157` 任意一次异常即 `_fail()` 置 failed |
| 生成二维码前 | 先 `waitForNodeReady(15s)` 再请求（`NodeLoginViews.swift:20-61`） | `LocalNodeLoginTransport` 20s ×3 次退避，**不等 Node 就绪**（`node_login_client.dart:45-60`），界面长期停留 loading 文案 |

### 1.3 修复要点
1. `node_login_client.dart`：将 `terminal` 语义显式建模（如 `NodeLoginErrorKind.terminal`），传输层不吞掉该标记。
2. `node_login_gateway.dart`：`poll.terminal` 时不再直接抛致命错，改为抛一个**可识别为终端**的异常，供控制器区分「瞬时失败」与「终端失效」。
3. `login_controller.dart`：
   - 引入 `consecutiveFailures` 连续失败计数（阈值对齐 iOS `maxConsecutiveFailures`）；
   - 引入 in-flight 护栏（上一次 poll 未返回则跳过本次）与 generation 代数护栏；
   - 终端态时自动 `regenerate()`，`autoRegenCount > maxAutoRegen` 才落失败态并提示「已自动刷新多次，请手动重新生成」；
   - 生成二维码前先等 Node 就绪（复用 `NodeRuntimeManager` 就绪语义），超时才失败。
4. `login_sheet.dart` / `node_login_gateway.dart`：多步（UCNode）与单步（115/夸克/百度）沿用同一套护栏（步骤切换走 `generation` 自增）。

### 1.4 验收标准
- Node 端模拟返回 `terminal=true`（任务已删）时，UI **自动换新码**并可继续扫码成功，最多自动刷新 N 次。
- 弱网下轮询偶发失败不直接落 failed，出现「轮询中…(重试)」类提示。
- 115 / 夸克 / UCNode / 百度 Node 在 Node 已就绪时，**不再出现长期「正在生成二维码…」转圈**；生成失败时给出明确错误文案。
- Node 未就绪时先生成等待，就绪后正常出码。

## 2. 【P0 · D 组】播放链 bdstoken 兜底与 Node 就绪判定 → 问题 4 / 5

### 2.1 现象
- 问题 4：点击百度播放链**直接闪退**，或报「播放失败：百度登录态正常，但未取得用户态 bdstoken，无法创建 vbox 转存目录」。
- 问题 5：点击百度「Node」资源报「百度网盘Node资源加载失败：Node 常驻系统未就绪，请稍后重试」，但授权页横幅却显示「Node 常驻系统 就绪 端口 58080 · 网盘解析链路可用」。

### 2.2 根因（Flutter vs iOS）
- **问题 4**：
  - `baidu_ibox_client.dart:1238-1252`：`fetchUserBdstoken` 取不到即抛该文案；该文件自述 **「不含 iOS 的 WebView 回退（C3）」**（`baidu_ibox_client.dart:1166`）。iOS 有 WebView 兜底抓 bdstoken（`CloudDriveAuthManager.swift:1262` `baiduEnrichAccountCookie` + C3 回退）。
  - 闪退：`pan_player.dart:480-482` 仅捕获 `BaiduIBoxException`，其他异常（如空指针 / 平台通道异常）未被兜住 → 冒泡到 UI 触发崩溃。
- **问题 5**：**两套就绪标准不一致**：
  - 横幅：`NodeRuntimeManager.isSystemReady`（HTTP 健康探活，`node_runtime_manager.dart:245-254` / `:328-336`）。
  - 播放解析：`NodePanClient._ensureOk` 把 `/spider/push/4/detail` 的 **502/503/404 直接映射为 `nodeUnavailable`**（`node_pan_client.dart:222-228`）→ 文案「Node 常驻系统未就绪」。
  - 即：进程活着但 **bundle spider 路由尚未就绪（返回 404）** → 出现「横幅就绪但解析报未就绪」的矛盾。iOS 靠启动 ack 握手 + 路由就绪避免此矛盾；Flutter 明确 **不移植 ack 握手**（`node_runtime_manager.dart:13`），且解析链不重试。

### 2.3 修复要点
1. **问题 5**：把「进程就绪」与「解析路由就绪」统一到同一判据。二选一：
   - 方案 a：`NodeRuntimeManager` 就绪判定**纳入解析端点探活**（探 `/spider/push/4/detail` 的一个轻量 id），路由未就绪前横幅不显示「就绪」；
   - 方案 b：`NodePanClient` 对 404/502/503 **加入短重试**（等待 bundle 路由预热），并在重试耗尽后才报未就绪，文案与横幅口径统一。
2. **问题 4（方案层）**：补齐 iBox 四层兜底之外的**用户态 bdstoken 获取兜底**（对齐 iOS C3 WebView 路径；桌面端若无法内嵌 WebView，退化为「引导用户手动粘贴 bdstoken / 走网页兜底」）。同时登录侧 `native_cloud_drive_login_gateway.dart:706` 的 `_enrichBaiduAccount` 需保证 `bdstoken/uk/username` **完整落库到凭据 extra**，供播放侧 `pan_player.dart:184` 的保存值兜底命中。
3. **问题 4（防闪退）**：`pan_player.dart` 百度分支扩大异常捕获面（除 `BaiduIBoxException` 外再兜一层），播放编排层统一转成 `PanPlayException` 文案，**任何情况不得冒泡到导致 App 闪退**。

### 2.4 验收标准
- 百度登录后（原生扫码）凭据 extra 中 `bdstoken` 非空；播放同一资源时优先命中保存值，不再报「未取得用户态 bdstoken」。
- 极端情况下（确实取不到 bdstoken）报明确可操作文案，**不闪退**。
- Node 引擎启动中点击 Node 播放：要么等待路由就绪后成功，要么报「解析链路准备中，请稍后重试」且**横幅此时不显示已就绪**（两者口径一致）。

## 3. 【P1 · B 组】登录成功不自动关闭二维码弹窗 → 问题 3 / 8

### 3.1 现象
- 问题 3：百度扫码成功拿到 token 后**不自动关闭**二维码弹窗。
- 问题 8：UC 原生扫码成功后不自动关闭，**需手动关第一页才出现 TV 登录二维码页**。

### 3.2 根因
- `login_sheet.dart:228-234`：`_onChanged` 在 `phase == success` 时**只置 `_succeeded` / 回调 `onLoginCompleted`，从不 `Navigator.maybePop()`**。iOS 所有扫码视图成功后均 `Task.sleep(800ms) → dismiss()`（`NodeLoginViews.swift:777-786`、`SettingsViews.swift:4934/4977` 等）。
- 问题 8 连锁：`login_sheet.dart:68-98` 的 UC 逻辑是「等第一个 sheet 关闭后 0.5s 再弹 TV 页」；因第一页不自关 → 必手动关。iOS 为 `NativeCloudQRLoginView` **自关** → `onChange(showUCNativeQR)` → 0.5s 弹 `UCTVAuthQRView`（`SettingsViews.swift:1670-1683`）。

### 3.3 修复要点
1. `login_sheet.dart`：`CloudDriveQrLoginSheet` 在成功态下**自动关弹窗**（保留 iOS 的约 800ms 停留让用户看到「登录成功」）。
2. UC 原生链路：确认成功后**自动关闭**第一页，再由 `openCloudDriveLoginSheet` 的 0.5s 延时逻辑自动弹 TV 授权页，**去掉「必须手动关」的前置条件**。
3. `CloudDriveUcTwoStepQrSheet`（`login_sheet.dart:516-546`）：第 1 步成功 600ms 自动切第 2 步 + 第 2 步成功自动关，与 iOS `NodeUcTwoStepLoginView` 一致（当前步骤切换逻辑已具备，补充最终自动关闭）。

### 3.4 验收标准
- 百度 / 夸克 / UC 原生扫码成功 → 弹窗**自动关闭**并回到授权中心已登录态。
- UC 原生扫码成功 → 第一页自动关闭 → 约 0.5s 后自动弹 TV 授权页，**全程无需手动关闭**。
- 多步（UCNode）两步走完自动关闭。

## 4. 【P1 · C 组】原生扫码轮询容错 / 会话不一致 → 问题 1 / 6

### 4.1 现象
- 问题 1：百度原生扫码后偶发「登录失败 · 百度轮询异常 errno=-1」。
- 问题 6：夸克原生扫码直接提示「登录请求已过期，请重新扫码登录」。

### 4.2 根因
- 百度：`native_cloud_drive_login_gateway.dart:670-677` 只要 `errno ∉ {0,1,2,3,4}` 立即抛「百度轮询异常 errno=$errno」。`errno` 来自 `_pickInt(json,['errno']) ?? -1`，即**响应体瞬时非 JSON / 空时被当成 errno=-1 并直接致命失败**；控制器无 iOS 的连续失败容忍（iOS 网络类错误可重试 5 次，`SettingsViews.swift:4900-4911`）。
  - 说明（如实登记不确定项）：iOS `baiduPollQrStatus` 对同样的非预期 errno 也会返回 `.failed`（`CloudDriveAuthManager.swift:1174-1204`），所以差异主要在**会话连续性 + 重试策略**（iOS URLSession cookie jar 连续轮询；Flutter 每次走 `SpiderHttpBridge`，抖动即判死）。
- 夸克：`native_cloud_drive_login_gateway.dart:897-905` 只把 `50004002/3/4` 当过期、`50004001` 当待扫，**其余一律抛异常**，未完整对齐 iOS 夸克状态码分支，且 start 无超时重试。

### 4.3 修复要点
1. 百度 `_baiduPoll`：区分「**响应不可解析/瞬时抖动**」与「**真·业务错误**」——前者按 pending 处理或计入连续失败重试，不立即 fatal；errno 兜底值不再直接当致命。
2. 夸克 `_quarkPoll`：补齐 iOS 状态码全分支映射（待扫 / 已扫 / 过期 / 需重试），start 失败加短重试。
3. `login_controller.dart`：与 A 组共用 `consecutiveFailures` 容错（原生 / Node 一致）。
4. 原生链路会话连续性：确认 `SpiderHttpBridge` 在轮询间**保持/复用 Cookie**，避免 channel 因缺 Cookie 返回异常 errno。

### 4.4 验收标准
- 轮询过程中注入一次「空响应 / 非 JSON」：**不落 failed**，自动下一次轮询继续。
- 夸克状态码各分支均有明确 UI 表现；过期才提示「二维码已过期，请重试」。
- 连续失败达阈值才提示「网络连接已中断，请重新生成二维码」。

## 5. 【P2 · E 组】授权中心动作矩阵错位 → 问题 11

### 5.1 现象
百度 / 夸克 / UC 卡片比 iOS 多出「Node扫码登录」入口；iOS 端只有「原生扫码 + 网页兜底」两个。

### 5.2 根因
- `cloud_drive_widgets.dart:54-68`：对 baidu/quark/uc 返回 3 个动作（含 `('Node扫码登录', ...)`）。
- iOS `providerAccountCard`（`SettingsViews.swift:1997-2061`）：`.uc` = 「原生扫码 + 网页登录兜底」；百度卡 = 「扫码授权 + 网页兜底」；夸克卡 = 「扫码登录 + 网页登录兜底」——**均为 2 项**。Node 档藏在**原生扫码 Sheet 内的 Segmented 切换**（`SettingsViews.swift:4415-4427` / `:4476-4492`）。
- Flutter 其实**也已在 Sheet 内做了**该 Segmented（`login_sheet.dart:257-289`），因此卡片按钮属**重复暴露**。

### 5.3 修复要点
- `cloud_drive_widgets.dart`：从 baidu/quark/uc 的动作列表**移除 `('Node扫码登录', ...)`**，恢复为 iOS 的 2 项；Node 入口仅保留在 Sheet 内 Segmented（已存在）。
- 注意：Node 托管派生卡（`baiduNode/quarkNode/ucNode/one15`）的「Node扫码登录」是 iOS `nodeManagedAccountCard` 的合法入口，**保留不动**。

### 5.4 验收标准
- 授权中心百度 / 夸克 / UC 卡片按钮数 = iOS（2 个），且 Sheet 内仍可切换原生 / Node。
- Node 派生卡入口不变。

## 6. 建议实施顺序

1. **P0-A（问题 2/7/9/10）**：Node 护栏落地 → 一次性修好整个 Node 扫码链。
2. **P0-D（问题 4/5）**：先修「不闪退 + 就绪口径一致」，再补 bdstoken 兜底。
3. **P1-B（问题 3/8）**：自动关闭 + UC TV 自动跟进（改动小、收益直观）。
4. **P1-C（问题 1/6）**：原生轮询容错，复用 A 组的连续失败机制。
5. **P2-E（问题 11）**：动作矩阵裁剪，回归对齐。

> 每组互相独立、可并行；A 组与 C 组共享 `login_controller.dart` 容错改造，建议先做 A 组的控制器护栏，C 组直接复用。

## 7. 结语（第 1–5 章）

11 条问题**全部**可追溯到「Flutter 端未对齐 iOS 端」，分属 A/B/C/D/E 五组根因，非彼此独立的偶发 bug。由于根因都在 Dart 层，**问题在于 Flutter 端整体而非仅 Windows**；Windows 只是暴露环境。唯一需要按平台分档的是问题 4 的 WebView 兜底能力。

### 8.2 关键结论（先讲清一个现实约束）

**Inno Setup 的向导是传统 VCL 窗口，无法实现上面这套 UI。** 具体来说：
- Inno 向导页版式固定（左侧大图 / 顶部标题 / 标准控件），**做不出「居中大 Logo + 5 张自定义步骤卡片」的布局**；
- `WizardStyle=modern` + `BackColor/BackColor2` 只能换配色和渐变，不能改版式；
- 左侧大图 `WizardImageFile` 是固定位置的位图面板，支持有限，**CSS 级流光/Lottie 效果无法实现**；
- 结论：**要 100% 还原定稿设计，必须加一层自定义 UI 壳**（路线 A）。

### 8.3 三条路线对比

| 维度 | **路线 A（推荐）** Inno 静默内核 + 自定义 UI 壳 | 路线 B（低成本）纯 Inno 近似 | 路线 C WiX Burn + WPF |
|---|---|---|---|
| 效果还原度 | **≈100%（可 1:1 还原预览）** | ≈50–60%（换配色 + 左图；版式仍是原生向导） | ≈100%（但需重做打包） |
| 改动量 | 中（Inno 逻辑**全部保留**，仅加壳 + 进度通道） | 小（只改 `.iss` + 准备图片帧） | 大（**换掉 Inno**，重写打包链） |
| 对现有 CI 影响 | 中（build-windows job 加两条构建步骤） | 极小 | 大 |
| 依赖 | WebView2 Runtime（Win10/11 通常已随 Edge 预装） | 无 | .NET + WiX Toolset |
| 风险 | 双 exe 嵌套；WebView2 缺失需兜底；壳需签名 | 达不到设计效果 | 打包链整体回归风险 |
| 适用 | 你现在的定稿设计 | 只想「别太丑」 | 长期重构打包 |

### 8.4 路线 A · 详细实施方案

#### 8.4.1 架构

```
vbox-setup.exe                      ← 用户双击的「壳」（单文件分发，保持 S.7 命名）
  ├─ 内嵌资源：vbox-installer-core.exe  （= 现有 installer.iss 编译产物，静默安装引擎）
  └─ UI：本地 HTML（本次定稿页面）由 WebView2 承载

运行流程：
  1) 壳启动 → 释放 core 到 %TEMP%\vbox-setup-<guid>\ → 立即显示 HTML 欢迎/目录页
  2) 目录页「浏览…」→ 壳调用原生文件夹选择器回填路径
  3) 点「安装」→ 壳执行：
       vbox-installer-core.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART /NOCANCEL
                                /DIR="<用户选择>"
                                /VBOXPROG="<壳与core约定的进度文件路径>"
  4) core 在 [Code] 各钩子写「阶段 + 进度」到 VBOXPROG 指定文件
  5) 壳轮询该文件 → 驱动 HTML 的进度条 / 5 步骤卡片
  6) core 退出 → 壳显示完成页 →（可选）启动 vbox.exe
```

#### 8.4.2 core 改造（`installer.iss`）——**保留全部既有逻辑，只增不减**

既有 `[Setup]` / `[Files]` / `[Icons]` / `[Run]` / `[Code]` 全部保持不变；仅追加进度上报钩子。

```ini

; 静默模式下不需要向导配色，但保留 modern 便于单独调试 core
WizardStyle=modern
```

```pascal
[Code]
{ ── 新增：进度上报通道（供 UI 壳轮询读取） ──────────────────────
  路径由壳通过自定义参数 /VBOXPROG=<path> 注入；
  {param:VBOXPROG} 需 Inno 6.x 支持，实现时需实测确认。             }

function ProgPath(): String;
begin
  Result := ExpandConstant('{param:VBOXPROG}');
  if Result = '' then
    Result := ExpandConstant('{tmp}\vbox-setup-progress.json');
end;

procedure ReportStage(const Stage: String);
begin
  SaveStringToFile(ProgPath(),
    '{"stage":"' + Stage + '","cur":-1,"max":-1}', False);
end;

{ 真实字节进度：Inno 内置事件（静默模式下是否触发需实测确认，
  若不触发则退化为「按阶段推进的估算进度」） }
procedure CurInstallProgressChanged(CurProgress, MaxProgress: Integer);
begin
  SaveStringToFile(ProgPath(),
    '{"stage":"","cur":' + IntToStr(CurProgress) +
    ',"max":' + IntToStr(MaxProgress) + '}', False);
end;

{ ── 阶段标记：与定稿 UI 的 5 张步骤卡片一一对应 ── }
function PrepareToInstall(var NeedsRestart: Boolean): String;
begin
  ReportStage('准备安装');
  Result := '';
  KillVboxProcesses();          { 既有逻辑，保持不变 }
end;

procedure CurStepChanged(CurStep: TSetupStep);
begin
  if CurStep = ssInstall     then ReportStage('解压程序文件');
  if CurStep = ssPostInstall then ReportStage('创建快捷方式');
end;

procedure DeinitializeSetup();
begin
  ReportStage('安装完成');
end;
```

> 说明：`PrepareToInstall` / `CurStepChanged` / `CurInstallProgressChanged` / `DeinitializeSetup` 均为 Inno 官方事件函数，**静默（`/VERYSILENT`）模式下依然会被调用**；其中 `CurInstallProgressChanged` 是否上报真实字节进度**需在实现阶段用一次 `/LOG` 实测确认**，若不生效则用「5 阶段 + 每阶段内插值」的估算进度兜底。

#### 8.4.3 壳（`vbox-setup-shell`）技术选型

| 选项 | 说明 | 建议 |
|---|---|---|
| **.NET 8 WPF + WebView2** | 用 WPF 做无边框窗口，WebView2 载本地 HTML；HTML 即定稿页面 | ✅ **首选**：能 1:1 复用已定稿的 HTML/CSS/动画 |
| .NET 8 WPF 纯自绘 | 不用 WebView，把 CSS 动画翻译成 WPF `Storyboard` | 备选：无 WebView2 依赖，但动画需重写，工作量大 |
| Tauri (Rust) | 体积小，同为 WebView 方案 | 一般：引入 Rust 构建链，收益不明显 |

**推荐：.NET 8 WPF + WebView2**（`Microsoft.Web.WebView2` NuGet）。理由：动画/布局直接用已定稿 HTML，改动面最小。

关键实现点（伪代码）：

```csharp
// 1) 释放内嵌 core 到临时目录
var corePath = Path.Combine(tempDir, "vbox-installer-core.exe");
ExtractEmbeddedResource("core/vbox-installer-core.exe", corePath);

// 2) 把 HTML 资源解包到 tempDir，WebView2 载入
webView.CoreWebView2.Navigate(new Uri(htmlPath).AbsoluteUri);

// 3) HTML 通过 WebMessage 与 C# 通信（选目录 / 开始安装 / 进度回报）
webView.CoreWebView2.WebMessageReceived += (s, e) => {
    var msg = JsonNode.Parse(e.WebMessageAsJson);
    switch ((string)msg["cmd"]) {
      case "browseDir":  ReplyPickFolder();  break;   // 原生 FolderBrowserDialog
      case "install":    StartCore(msg["dir"]); break;
    }
};

// 4) 轮询进度文件 → 推给 HTML
var progFile = Path.Combine(tempDir, "vbox-setup-progress.json");
var timer = new DispatcherTimer { Interval = TimeSpan.FromMilliseconds(150) };
timer.Tick += (s, e) => {
    if (File.Exists(progFile)) {
        var json = File.ReadAllText(progFile);   // core 用 SaveStringToFile 原子写
        webView.CoreWebView2.PostWebMessageAsJson(json);
    }
};

// 5) 启动 core（静默）
var psi = new ProcessStartInfo(corePath, string.Join(" ", new[]{
    "/VERYSILENT", "/SUPPRESSMSGBOXES", "/NORESTART", "/NOCANCEL",
    $"/DIR=\"{dir}\"", $"/VBOXPROG=\"{progFile}\""
})) { UseShellExecute = false };
psi.StartInfo... ; Process.Start(psi);
```

> **重要**：定稿 HTML 需做一处适配——把「▶ 演示安装」按钮换成真实控制流（`browseDir` / `install` 消息），进度由 core 的真实数据驱动（不再用 `requestAnimationFrame` 假进度）。这部分可在现有预览 HTML 基础上直接改。

#### 8.4.6 风险与对策

| 风险 | 对策 |
|---|---|
| WebView2 Runtime 缺失（罕见老系统） | 检测 `CoreWebView2Environment` 创建失败 → 回退调用 core 的**原生向导模式**（去掉 `/VERYSILENT`），保证「装得上」优先 |
| 壳未签名 → SmartScreen 拦截 | 走 S.6 的 Windows 代码签名（可选但建议） |
| `/VERYSILENT` 下 `CurInstallProgressChanged` 不触发 | 实现期用 `/LOG` 实测；不触发则退化为「5 阶段 + 阶段内插值」估算进度 |
| `{param:VBOXPROG}` 参数注入在 Inno 6 的可用性 | 实现期实测；不可用则改为写固定 `%TEMP%\vbox-setup-progress.json`（壳/核约定同一路径） |
| 双 exe 嵌套 + UAC | `PrivilegesRequired=lowest` 已是免管理员，core 继承用户态即可；壳不额外申请提权 |
| 单文件发布体积（self-contained .NET ≈ 数十 MB） | 若在意体积，改为 framework-dependent 或纯 WPF 自绘（去掉 WebView2/HTML 依赖） |

### 8.5 落地顺序建议

3. **壳搭建**：`windows/setup-shell` 最小可用版（无边框窗口 + WebView2 + 释放 core + 进度轮询）。
4. **CI 接线**：按 8.4.4 改造 `build-windows` job，产出改名后的 `vbox-setup.exe`。
