## 1. 内核多平台可用性（回应「MPVKit/MoltenVK/MDK 能否多端使用」）

### 1.1 平台支持矩阵（外部事实 + 仓库实测）

| 内核 | 官方平台支持 | 仓库内实物 | Flutter 四端可用性 |
|---|---|---|---|
| **MoltenVK** | **仅 Apple**（Vulkan → Metal 转译层） | — | ❌ **不需要**：Windows 用原生 Vulkan/D3D11，Android 用 Vulkan/GLES，无 Vulkan 需求的场景逆向后端本身即可 |
| **MPVKit** | **仅 Apple**（libmpv 的 xcframework 封装） | `vbox/Libraries/MPV/MPVKit.xcframework` 实测**仅 2 个 slice**：`ios-arm64` / `ios-arm64_x86_64-simulator`——**连 macOS slice 都没有** | ❌ 直接用不了（且 macOS 也缺）；但其**底层 libmpv 全平台可用** |
| **MDK** | ✅ **跨平台**：Windows(x86/arm) · UWP · Linux · **macOS** · **Android** · **Android TV** · iOS/tvOS/visionOS · OpenHarmony · 树莓派/RockChip，**全平台硬解** | iOS 侧有 `MDKPlayerEngine.swift` / `MDKRenderView.swift` / `MDKPipManager.swift` | ✅ **可一统四端** |

### 1.2 判定：障碍不在平台，在「渲染输出面」

- **「能不能跑」不是平台限制问题**：libmpv 与 MDK 均为跨平台内核。v1.3 §2 已证：四端缺的是**渲染输出面**（Texture/Surface/RenderView），不是内核本身不可用。
- 换言之：**换内核不解决当前问题**；**接上输出面**才解决。

### 1.3 值得决策：MDK 作为「一统四端」候选

| 维度 | 现方案（异构拼装） | MDK 单内核方案 |
|---|---|---|
| Windows | libmpv（`vo=null`，渲染层待补） | MDK（含渲染） |
| macOS | AVPlayer（复杂封装失败）→ 待补 libmpv | MDK（含渲染） |
| Android / TV | Media3（无 Surface）→ libVLC 待补 | MDK（含渲染 + Android TV 官方支持） |
| 硬解 | 各端分别接（hwdec / MediaCodec / VT） | **SDK 内统一提供全平台硬解** |
| 代价 | 三套原生实现 + 三套渲染接线 | **闭源二进制**（免费）；须与 iOS 现有 MPVKit/MDK 双轨做一致性取舍 |

> **建议**：将「是否以 MDK 统一四端播放内核」列为**架构决策项**（编号建议 **C-补·内核选型**），与 v1.3 的 **G-02-R（渲染层）** 一并评审。若选 MDK，可显著减少三端渲染接线的重复工作。

## 2. 封面图：纠正 v1.3 §3 的乐观结论

### 2.1 结论修正

| 版本 | 判定 | 问题 |
|---|---|---|
| v1.2 §6 | 「Flutter **直连**豆瓣图片」 | 表述错误（直连必 403） |

| **v1.4（本版）** | **判定为「部分/未交付」**，建议改为**对齐 iOS 的统一代理入口** | — |

### 2.2 事实核查（避免误判）

| 核查点 | 实测结果 |
|---|---|
| `PlatformAsyncImage` 是否被引用 | ✅ **20+ 处**（首页/搜索/详情/豆瓣/福利/单平台/直播/短剧/音乐/海报卡/源发现），**非零引用** |
| 是否收敛为统一组件 | ✅ 是（`vbox_poster_card.dart:144` 亦收敛至它） |
| `Image.network` 的 `headers` 是否支持 | ✅ Flutter 官方：`NetworkImage.headers` 经 `HttpClient.get` 发送，**仅 Web 平台忽略**；Android/iOS/Windows/macOS/Linux **生效** |
| 防盗链头是否已注入 | ✅ `doubanHeadersFor`（`platform_async_image.dart:194-206`）注入 `Referer: https://movie.douban.com/` + iPhone UA + Accept；`kDoubanImageHosts` 13 主机 |
| **失败是否可诊断** | ❌ **不可**——`errorBuilder` 与 `loadingBuilder` 均直接返回占位盒，**失败静默**，无原因上报 |

> **推断**：技术上"应该能显示"与运行期"不显示"矛盾 → 存在**具体故障**（候选：`http://`→`https://` 升迁后 CDN 不支持 / 证书 / UA+Referer 组合仍被拒 / 源侧 `vod_pic` 为空），且**当前无诊断手段可定位**。**必须补可观测**方能定因。

### 2.3 架构差异（为何「对齐 iOS」确实更好）

iOS 是**统一代理入口**，Flutter 是**分散 headers 注入**：

| 维度 | iOS（`DoubanImageProxyServer`） | Flutter 现状 |
|---|---|---|
| 形态 | `proxiedURL(for:)` / `markedURLString(for:)` 把封面**重写**为 `http://127.0.0.1:18080/...`；`proxy://` 为内部标记前缀 | 每处各自 `Image.network(headers:)` |
| 调用方负担 | 一句 `proxiedURL(for: pic)`；**任何图片组件都能显示**（返回的是普通 http 图片） | 依赖组件具备 headers 能力；**Web 端直接失效** |
| 统一处理 | header / SSL / `http→https` / 缓存（`NSCache` 80MB·300）**全在代理侧** | 散落各组件内 |
| 覆盖面 | **豆瓣 + TMDB + 福利平台共用入口**（实测调用：`DoubanHomeView` / `DoubanCategoryBrowserView` / `DoubanRankingView` / `TMDBService.proxiedURL` / `WelfareProxyStore.proxiedURL` / `FuliPlatformService`） | 仅 `kDoubanImageHosts` 13 主机判断 |
| 视频流 | 同套 `proxiedStreamURL`（百度等网盘） | go-proxy **无图片路由** |

### 2.4 建议方案：把 go-proxy 扩为统一图片代理

**理由**：
1. **多封面关联天然统一**——豆瓣/TMDB/福利等**多域封面收敛到一个入口**，不再各写一套、不再漏（这正是本轮提问的关切点）。
2. **组件无关**——本地代理回吐普通 `http` 图片，不依赖 headers 能力，**规避 Web 限制**。
3. **集中治理**——header / SSL / `http→https` / 缓存 / 降级集中一处。
4. **成本低**——Flutter **已有 go-proxy 本地 HTTP 服务**（`go-proxy/`：`proxy.go` 路由 + `cache.go` 磁盘 `DiskCache` + `go_proxy_client.dart` + 三端插件），**新增一条 `/image` 路由 + 主机白名单即可**（对齐 `allowedHosts` 13 主机 + `proxiedURL` 语义）。

**配套（必须）**：
- 封面加载 **失败可观测**：`errorBuilder` 上报状态码/主机/原因（替代当前静默占位），否则故障无法定位。
- 与 §1.3 的网盘流代理（`proxiedStreamURL`）**共用同一 go-proxy 实例与缓存目录**，避免两套本地服务。

> 编号建议：**F-补·封面统一代理（go-proxy /image）** 与 **F-补·网盘原生直链播放**（v1.3 §4）**合并为一条 go-proxy 扩展工作项**，统一设计端口/路由/白名单/缓存。
