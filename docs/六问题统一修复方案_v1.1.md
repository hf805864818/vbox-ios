## 1. 问题 1 · 夸克原生扫码「登录请求已过期，请重新扫码登录」

### 1.1 现象
vbox 端展示夸克登录二维码 → 夸克 App 扫码成功 → 在夸克 App 内点击「确认登录」时，**夸克 App 自己的页面**立即提示「登录请求已过期，请重新扫码登录」。注意：该文案由**夸克 App 渲染**，并非 vbox 弹出；Node 端同流程正常。

### 1.2 根因分析（v1.1 修正）

**结论：夸克二维码 payload / 轮询使用的 `client_id=532` 与铸造 token 时使用的 `client_id=386` 不一致，导致夸克 App 确认登录时被服务端判定为「请求已过期」而拒绝。**

> 更正说明：v1.0 曾判定为「服务端 message 透传 / 轮询生命周期」问题。经三端（Flutter / iOS / Node）实现逐字比对，该判断**不成立**——「过期」发生在**扫码确认**环节（App 内），早于 vbox 轮询拿 ticket，与轮询生命周期无关。真正差异是 `client_id` 前后不一致。

证据链（三端对比）：

**① 铸造 token：三端都用 `client_id=386`**
- Flutter：`native_cloud_drive_login_gateway.dart:141` `_quarkQrClientId = '386'`；`_quarkStart`（`860-895`）请求 `uop.quark.cn/cas/ajax/getTokenForQrcodeLogin?...&client_id=386&v=1.2&request_id=...`
- iOS：`CloudDriveManager.swift:4308` `quarkCreateQrToken(clientId: "386", pollClientId: "532")`
- Node（正常参照）：`assets/noderuntime/bundles/kstore_index.js` 的 `startQuark` 请求 `getTokenForQrcodeLogin?...&client_id=386&v=1.2&request_id=...`

**② 二维码 payload + 轮询：Flutter / iOS 改用 `532`，Node 仍用 `386`（关键分歧）**
- Flutter：`_quarkQrPayload`（`989-996`）把 `_quarkPollClientId`(=532) 拼进二维码 URL；`_quarkPoll`（`897-948`，`902-909`）轮询 `getServiceTicketByQrcodeToken?...&client_id=532...`
- Flutter 常量：`native_cloud_drive_login_gateway.dart:142` `_quarkPollClientId = '532'`
- iOS：`CloudDriveManager.swift:4340` `qrPayload = quarkQRCodePayload(token:, clientId: pollClientId)`；`4344-4354` payload `client_id=532`；`4357-4393` poll `client_id=token.pollClientId`(=532)。源码注释（`4287`）自述「生成 token 时使用 386；轮询时 PC 抓包用 532，这里都保留」——即 532 是**人为按抓包改写**，并非与 token 匹配。
- Node：`startQuark` 生成的 `qrUrl` 为 `https://su.quark.cn/4_eMHBJ?token=...&client_id=386&...`；`pollQuark` 轮询 `...&client_id=386...`——**全程 386**。

**③ 服务端语义**：`getTokenForQrcodeLogin` 铸造出的 token 绑定发起铸造的 `client_id`；二维码里携带的 `client_id` 是夸克 App 扫码后回传/确认时使用的业务方标识。当二维码 `client_id`(532) 与 token 归属 `client_id`(386) 不一致，夸克 App 确认时服务端校验不通过，直接回「登录请求已过期」——这正是「App 内提示过期」的由来（与 vbox 轮询无关）。

**④ 次要差异（可能叠加影响）**：Node 的二维码 URL 还额外带 `sch=pckk@other_ch&sve=3.1.8`，且 `sys=win32`；Flutter/iOS 缺这两个参数、`sys=darwin`。这会让二维码的「渠道 / 客户端版本」与服务端 PC 抓包口径不一致，属加固项。

**⑤ 兑换（exchange）口径不同（扫码通过后才涉及，非本次报错主因）**：
- Node：`pan.quark.cn/desktop/account/login?pr=ucpro&fr=pc&sys=win32&st=...`，读 `data.pus`/`data.uid` 后调 `refreshCookieUrl`。
- Flutter：`_quarkExchange`（`950-986`）`pan.quark.cn/account/info?st=...&fr=pc&platform=pc`；iOS：`CloudDriveManager.swift:4396-4415` 同为 `account/info`。
- 说明：`account/info` 为兼容旧接口（`CloudDriveAuthManager.swift:771-773` 也把它当 UC 兜底）。即便扫码能通过，后续兑换也可能与 Node 行为不一致，建议一并统一。

### 1.3 iOS 对照
iOS `quarkPollQrStatus`（`CloudDriveManager.swift:4357-4393`）状态码口径与 Flutter 一致，且**同样存在 386 铸造 / 532 二维码+轮询的分叉**——即问题 1 并非 Flutter 独有，iOS 为同源缺陷（修复需两端同步）。

### 1.4 修复方案

**首选（治本，对齐 Node 正常实现）**：
1. 让二维码 payload 与轮询的 `client_id` **回归 token 铸造值 `386`**——二维码与 `getServiceTicketByQrcodeToken` 都用 `386`，删除/停用 `_quarkPollClientId=532` 这条分叉。
   - Flutter：`native_cloud_drive_login_gateway.dart:142 / 989-996 / 902-909`
   - iOS：`CloudDriveManager.swift:4308 / 4340-4354 / 4357-4393`（连同 `4287` 注释一并订正）
2. 二维码 URL 补齐 Node 参数：`sch=pckk@other_ch&sve=3.1.8`；并将 `sys` 对齐 `win32`（若服务端对 `sys` 有校验）。
3. 兑换接口对齐 Node：改用 `pan.quark.cn/desktop/account/login?pr=ucpro&fr=pc&sys=win32&st=...`，解析 `data.pus`/`data.uid` 后再走 `refreshCookieUrl`；若暂不改接口，则至少保证 `account/info` 能拿到 `__kps/__pus/__uid`。

**备选（仅补诊断，不治本）**：保留 532 分叉的同时，在 `_quarkPoll` 的 message 透传分支（`944-947`）记录 `status` 原值与完整 `json`，用于对照服务端返回——但这无法解决「App 内过期」，仅作辅助。

### 1.5 验收
- vbox 展示二维码 → 夸克 App 扫码 → 点击「确认登录」不再出现「登录请求已过期」，vbox 能收到 ticket 并完成兑换。
- Flutter 与 iOS 二维码 payload / 轮询 / 兑换三处 `client_id` 均为 `386`，与 Node 一致。
- （回归）UC 兜底 `account/info` 路径不受影响。

## 2. 问题 2 · UC 扫码已获 token，播放报 `create code=31001 require login [guest]`

### 2.1 现象
UC 网盘原生扫码已成功拿到登录 token，但播放时创建转存目录失败：
`UC: Cookie 可能已失效，请重新登录 (create code=31001 msg=require login [guest])`；Node 端正常。

### 2.2 根因分析

**结论：`SpiderHttpBridge` 的 cookie jar 覆盖了调用方显式传入的登录 Cookie，导致 create 请求以 guest 身份发出 → 31001。**

证据链：

1. `uc_native_client.dart:498-552` `ensureFolder` 在 create 失败且 `code != 23008` 时抛错（`535-540`）：
   `'UC: Cookie 可能已失效，请重新登录 (create code=$code msg=...)'` —— 即 31001 的报错来源。
2. `uc_native_client.dart:244-255` `_commonHeaders(cookie)` **显式携带**登录 Cookie。
3. 但请求经 `SpiderHttpBridge.request` 时，`spider_http_bridge.dart:440-443` **无条件用 cookie jar 结果覆盖显式 Cookie 头**：

```dart
final String? cookie = _cookieStore.cookieHeaderFor(uri);
if (cookie != null) {
  headers[HttpHeaders.cookieHeader] = cookie;   // ← 覆盖调用方显式 Cookie
}
```

UC 的 create 请求命中 `drive.uc.cn`，其 cookie jar 中若有残留/不含登录态，就会覆盖掉 `_commonHeaders` 里的正确登录 Cookie → 服务端识别为 guest → 31001。

4. 对照 iOS：`CloudDriveManager.swift:8366-8432` `resolveUCPlayURL` 会**合并 + 持久化**刷新后的 Cookie；`8803-8901` `ucEnsureFolderWithCookie` 返回 `(folderId, mergedCookie)`。Flutter 的 `ensureFolder` 只返回 `String fid`，**不做 Cookie 合并回写**——这是与 iOS 的实质差异。

### 2.3 修复方案

**修复 A（传输层，根治覆盖问题）**：为 `SpiderHttpBridge.request` 增加 cookie 策略开关（如 `cookieMode: explicitWins | jarWins | merge`）。当调用方已显式传入 `Cookie` 头时，**不再被 jar 覆盖**；默认对显式 Cookie 采用「显式优先、jar 补充缺失项」的合并策略。

**修复 B（业务层，对齐 iOS）**：`uc_native_client.ensureFolder` 改为返回 `(fid, mergedCookie)`，把响应 `Set-Cookie` 合并回写；`pan_player` 侧用合并后的 Cookie 继续后续请求（对齐 `CloudDriveManager.swift:8803-8901`）。

**修复 C（登录态落库）**：确认扫码成功后把 UC 登录 Cookie 正确写入 `SpiderHttpBridge` 的 cookie store，避免后续请求 jar 内为空。

> 建议 A + B 同做：A 消除覆盖这一结构性缺陷，B 补齐 iOS 已有的 Cookie 刷新回写能力。

### 2.4 验收
- UC 扫码后播放，`create` 请求不再出现 31001。
- 断网重试 / 长时播放后 Cookie 刷新仍能正确合并，不再回落 guest。

## 3. 问题 3 · 百度路链播放报「未取得用户态 bdstoken」

### 3.1 现象
详情页点百度路链播放，报：
`百度登录态正常，但未取得用户态 bdstoken，无法创建 vbox 转存目录`；Node 端正常。

### 3.2 根因分析

**结论：bdstoken 四层兜底中，第 3 层（WebView）因未接线而恒为空；同时活取成功的结果未落库，导致后续复用失败。**

证据链：

1. 报错来源：`baidu_ibox_client.dart:1243-1251`，`fetchUserBdstoken` 返回空即抛该 message。
2. `fetchUserBdstoken`（`baidu_ibox_client.dart:742-787`）四层：
   - 第 1 层 `gettemplatevariable`（`747-765`）
   - 第 2 层 抓 `disk/main` 页面 HTML（`766-776`）
   - 第 3 层 **WebView**（`779-783`）→ 调用 `_webViewBdstoken`
   - 第 4 层 回退授权中心保存值 `savedBdstoken`（`784-785`）
3. **第 3 层实际是死代码**：`baidu_ibox_client.dart:134` 默认注入 `UnavailableWebViewBridge()`：
   ```dart
   _webView = webView ?? const UnavailableWebViewBridge(),
   ```
   而 `pan_player.dart:97` 构造 `BaiduIBoxClient()` 时**未传入 WebView 实现**，故 `_webViewBdstoken` 恒返回空。
4. 活取成功回调 `onFetched`（`762/774/781`）用于回写凭据，但需确认调用链是否真正落库（对齐 iOS `saveBdstokenCredential`，`CloudDriveManager.swift:4761`）。

### 3.3 iOS 对照
iOS 通过 WKWebView 载入 `disk/main` 复用 CookieJar 拿用户态 bdstoken（`baiduFetchUserBdstokenViaWebView`），并把结果持久化到授权中心。Flutter 侧 WebView 桥存在（`InAppWebViewBridge`）但未注入到 `BaiduIBoxClient`。

### 3.4 修复方案

1. **接线 WebView 兜底**：在 `pan_player.dart:97` 构造 `BaiduIBoxClient` 时注入真实的 `InAppWebViewBridge`（替换 `UnavailableWebViewBridge`），使第 3 层兜底生效。
   - **平台覆盖**：`InAppWebViewBridge.isAvailable` 对 Android / iOS / macOS / **Windows** 均为 true。Windows 由 `flutter_inappwebview_windows`（Microsoft.Web.WebView2 承载）提供 `HeadlessInAppWebView` / `CookieManager` / `InAppWebView`，与 Android/iOS/macOS 走同一套 API（插件已在 `windows/flutter/generated_plugin_registrant.cc` 注册）；`main()` 启动时经 `InAppWebViewBridge.initialize()` 创建**自定义数据目录**的 `WebViewEnvironment`（并探测 WebView2 Runtime，缺失或创建失败则 Windows 上 `isAvailable=false` 静默降级）；仅 Linux 无插件实现，`isAvailable=false`，第 3 层自动空返回、继续走第 4 层保存值兜底，行为与接线前一致。
2. **确认活取落库**：核对 `pan_player.dart:479-490` 的 `onBdstokenFetched` → `_saveBaiduBdstoken`（`189-208`）链路，确保 `gettemplatevariable` / `disk-main-html` / `webview` 任一来源成功后写入凭据 `extra['bdstoken']`，供第 4 层复用。
3. **登录补全前置**：确认 `_enrichBaiduAccount`（`native_cloud_drive_login_gateway.dart:737-804`）在取 bdstoken 前已把 BFESS 等 Cookie 补全（二次 `fetchUserFields`）。

### 3.5 验收
- 百度路链播放不再报「未取得用户态 bdstoken」。
- 首次活取成功后，二次播放能命中保存值（第 4 层）。
- 平台覆盖：Android / Android TV / iOS / macOS / **Windows** 均走第 3 层 WebView 兜底（Windows 需 WebView2 Runtime，缺失时自动回退第 4 层）；仅 Linux 回退第 4 层保存值。

## 4. 问题 4 · 详情页点剧集要停留一会才出播放器

### 4.1 现象
详情页点剧集资源，要停留一会才弹出播放器；iOS 点击即出播放器（先出界面后加载）。

### 4.2 根因分析

**结论：Flutter 采用「先 resolve 后 push」，iOS 采用「先 present 后 resolve」。**

- Flutter `detail_page.dart:360-439` `_play`：
  - `393` `setState(() => _playing = true)`
  - `395-396` **先** `await _uc.resolvePlayUrl(...)`（网络解析，耗时）
  - `415` 解析成功后才 `Navigator.push(PlayerPage...)`
- 网盘路径 `_playPanLink`（`detail_page.dart:959-1013`）同型：`972` 先 `await _pan.prepare(...)`，`993` 才 push。
- iOS `vbox/Views/PlayerViews.swift:950-960` `handleEpisodeSelect` **同步**设置 `playerLaunchData`，`.fullScreenCover(item:)`（`1098-1100`）**立即呈现**播放器，解析在播放器内进行。

### 4.3 修复方案

**改为「先 push 播放器，再在播放器内 resolve」**，与 iOS 一致。基础设施已就绪：

- `PlayerPage` 已支持 `onResolveEpisode: _resolveEpisodeSource`（`detail_page.dart:428`）。
- 做法：`_play` 不再 `await resolve`，而是**立即** `Navigator.push(PlayerPage)`，把「待解析的剧集信息 + resolve 回调」交给播放器；播放器显示加载态并自行调用解析。`_playPanLink` 同理，把 `_pan.prepare/sourceFor` 下沉到播放器侧。

### 4.4 验收
- 点击剧集后播放器**立即出现**（含加载态），不再有可感知的等待空窗。
- 解析失败时播放器内给出错误提示，可返回。

## 5. 问题 5 · 播放视频泛黄（采用方案 A：对齐 iOS 的 GPU 渲染）

### 5.1 现象
播放视频画质与原视频不同，整体**泛黄**（偏暖）。用户提供截图：Windows 端 vbox 窗口内视频偏黄；另一张蓝底「保护正版 人人有责」画面蓝色正常。

### 5.2 先定内核：桌面端用的是 **libmpv**（自研原生插件）

| 平台 | 播放内核 | 渲染实现 |
|---|---|---|
| Android | Media3(ExoPlayer) 主 + libVLC 回退 | 自研 Kotlin 插件（**不含 libmpv**） |
| Windows | **libmpv** | 自研 C++ 插件 |
| macOS | **libmpv** | 自研 Swift 插件 |
| iOS | nativeiOS（AVPlayer + MDK/MPVKit） | 原生 Swift 栈 |

- 后端链：`lib/domain/entities/player/player.dart:305-321` —— `windows/macos → [libmpv]`；`android → [media3, mdk, libVLC]`。
- Android 插件仅实现 media3 / libVLC：`android/app/src/main/kotlin/com/vbox/player/PlayerPlugin.kt:264-271`（其它后端直接报「未知后端」）；Android 依赖无 mpv/mdk：`android/app/build.gradle.kts:144-147`。

> 结论：泛黄截图是 **Windows 窗口**，且 Android 不走 libmpv → 问题 5 **100% 落在 Windows/macOS 的 libmpv 渲染路径**。

### 5.3 根因：桌面 libmpv 走 **SW 软渲染**，缺少 GPU 色彩管理

**Windows**（`windows/runner/player_plugin.cpp`）：
- `402` 设 `vo=libmpv`；`469-491` `SetupRenderContext` 用 **`kRenderApiSw`**（= `"sw"`，`player_plugin.h:89`）创建 render context；
- `RenderFrame`（`542-598`）用 `MPV_RENDER_PARAM_SW_SIZE/SW_FORMAT("bgra")/SW_STRIDE/SW_POINTER` 逐帧**软渲染**为 BGRA；
- `CopyPixelBuffer`（`600-615`）把 BGRA 缓冲交 Flutter `PixelBufferTexture` 上屏。

**macOS**（`macos/Runner/PlayerPlugin.swift`）：
- `620` 设 `vo=libmpv`；`setupMpvRenderContext`（`838-876`）用字面量 **`"sw"`**；
- `renderMpvFrame`（`888-957`）同样 SW 参数 + `"bgra"`；`makePixelBuffer`（`960-991`）→ `kCVPixelFormatType_32BGRA`。

**为何泛黄**：`MPV_RENDER_API_TYPE_SW` 由 libswscale 只做 **YUV→RGB 矩阵转换**，**不做 primaries / gamma(TRC) / HDR tone-mapping**。当片源色彩标签缺失或与 mpv 默认假设不一致时，RGB 输出整体偏移 → 泛黄/偏暖。同时全仓（含 iOS PlayerCore）**未设置任何 `target-prim/target-trc/target-colorspace/icc-profile/tone-mapping`**（检索零命中），SW 路径也无从补偿。

**iOS 为何不泛黄**：iOS 的 libmpv 内核走 **GPU render context**（`MPV_RENDER_API_TYPE_OPENGL`），色彩管理在 GPU 上完成：
- `vbox/PlayerCore/LibmpvMoltenVKPlayerCore.swift:690-700`：`vo=libmpv` + `gpu-api=opengl` + `opengl-es=yes`；
- `vbox/PlayerCore/MPVRenderContextPlayerCore.swift:206-214`：`vo=libmpv` + `gpu-api=opengl` + `opengl-es=yes`；
- 渲染上下文创建：`LibmpvMoltenVKPlayerCore.swift:738-789` / `MPVRenderContextPlayerCore.swift:256-293` —— 用 `MPV_RENDER_PARAM_OPENGL_INIT_PARAMS` + `MPV_RENDER_PARAM_ADVANCED_CONTROL`，渲染用 `MPV_RENDER_PARAM_OPENGL_FBO` + `MPV_RENDER_PARAM_FLIP_Y`。
- 注意：iOS **也没有**设置任何 `target-*` 色彩选项 —— 靠的正是 GPU 渲染路径的**自动色彩管理**。这与「方案 A」的方向一致。

> 结论：差异不在色彩选项，而在**渲染后端**——iOS 用 OpenGL(GPU)，桌面用 SW。因此「对齐 iOS」= 桌面改走 OpenGL render context。

### 5.4 修复方案 A（治本，对齐 iOS）：桌面 SW → OpenGL(GPU) render context

**核心改动**：把 Windows/macOS 的 render context 从 `MPV_RENDER_API_TYPE_SW` 换成 `MPV_RENDER_API_TYPE_OPENGL`，并设 `gpu-api=opengl`，让 mpv 在 GPU 上跑完整色彩管线；Flutter 纹理上屏管线**保持不变**（改由 `glReadPixels` 回读 BGRA）。

**Windows（`player_plugin.cpp` / `player_plugin.h`）**
1. 枚举值已就绪：`player_plugin.h:59-81` 已声明 `MPV_RENDER_PARAM_OPENGL_INIT_PARAMS(2)` / `OPENGL_FBO(3)` / `FLIP_Y(4)` / `ADVANCED_CONTROL(10)`，无需改 ABI 顺序；新增 `kRenderApiGl = "opengl"`。
2. 新增 `mpv_opengl_init_params` 结构与 `get_proc_address`（`wglGetProcAddress` 包装，回退 `GetProcAddress(opengl32.dll)`）。
3. `InitializeMpv`（`392-429`）：在 `set_option_string(vo, "libmpv")` 后追加 `gpu-api=opengl`。
4. `SetupRenderContext`（`469-491`）：在渲染线程上创建**隐藏窗口 + WGL 上下文**（`ChoosePixelFormat`/`wglCreateContext`/`wglMakeCurrent`），用 `MPV_RENDER_API_TYPE_OPENGL` + `OPENGL_INIT_PARAMS` + `ADVANCED_CONTROL` 创建 render context。
5. `RenderFrame`（`542-598`）：改为 `glGenFramebuffers`/`glGenTextures` 建离屏 FBO → `MPV_RENDER_PARAM_OPENGL_FBO`（`internal_format=0`）+ `MPV_RENDER_PARAM_FLIP_Y` 渲染 → `glReadPixels(GL_BGRA,...)` 回读到 `frame_buffer_`（保持 BGRA8888，`player_plugin.h:201`）→ 现有 `MarkTextureFrameAvailable` 上屏逻辑不变。
6. 线程亲和：WGL 上下文须在渲染线程 `wglMakeCurrent`；`ShutdownMpv`（`431-465`）补 `wglDeleteContext`/销毁隐藏窗口。

**macOS（`PlayerPlugin.swift`）**
1. `setupMpvRenderContext`（`838-876`）：`"sw"` → `"opengl"`，并加 `MPV_RENDER_PARAM_OPENGL_INIT_PARAMS` + `ADVANCED_CONTROL`（`get_proc_address` 用 `dlsym`，参照 iOS `LibmpvMoltenVKPlayerCore.swift:750-756`）。
2. `openWithMpv`（`593-685`）：追加 `setOption("gpu-api", "opengl")`（**不要**设 `opengl-es`，macOS 用桌面 GL）。
3. 创建 `NSOpenGLContext`/CGL 上下文（或 `NSOpenGLPixelFormat` + `NSOpenGLContext`），在渲染线程 makeCurrent。
4. `renderMpvFrame`（`888-957`）：SW 参数 → `MPV_RENDER_PARAM_OPENGL_FBO` + `FLIP_Y`；再 `glReadPixels` 回读 BGRA，`makePixelBuffer`（`960-991`）保持不变。

**对齐原则**：与 iOS 一致，**不额外设置** `target-prim/target-trc/tone-mapping`（iOS 亦未设），依赖 GPU vo 的自动色彩管理；HDR 片源由 GPU 路径的 tone-mapping 默认策略处理。

**关于上屏方式的两种子方案**：
- **A1（推荐先做）**：OpenGL render context + `glReadPixels` 回读到现有 Flutter 纹理。**Dart 侧零改动**，颜色即刻对齐 iOS；代价是每帧一次 GPU→CPU 回读（与现 SW 同量级）。
- **A2（后续可选）**：改用原生 GL/Metal 表面直接呈现（Windows `FlutterDesktopGpuSurfaceDescriptor` / macOS `IOSurface`），消除回读开销；改动面更大，列为后续优化。

1. 修复前先确认：播放时读 `video-params/primaries`、`gamma`、`colormatrix`、`range`，或开 `msg-level=vo=v,sws=v` 观察 swscale 色彩转换告警。
2. 修复后用**同一段片源同一帧**截图比对 R/G/B 通道值，并与 iOS 端同帧对比。
3. 回归：Windows/macOS 播放（点播/直播/HDR/复杂封装）、PiP、切集、纹理尺寸变更事件正常。

### 5.6 验收
- 桌面端播放同一片源颜色与 iOS 端一致，泛黄消失。

## 6. 问题 6 · Android 切源分类一排 2 个（iOS 3 个）

### 6.1 现象
Android 端「切源分类」数据网格一排只有 2 个，iOS 一排 3 个。

### 6.2 根因分析

**结论：`ResponsiveGrid` 竖屏按宽度断点，`<480dp` 判 2 列；iOS 竖屏固定 3 列。**

- `lib/presentation/widgets/adaptive/responsive_grid.dart:47` `portraitWideBreakpoint = 480`；
- `55-63` `columnsFor`：`form.isPortrait` 时 `width >= 480 ? 3 : 2` —— 手机竖屏宽度普遍 `<480dp` → **恒为 2 列**。
- iOS 为**固定 3 列**：`vbox/Views/SourceDiscoveryView.swift:540-548`（3 × `GridItem(.flexible(), spacing: 12)`）；`CategoryDetailView.swift:291-295 / 467-471` 同为 3 列。

### 6.3 修复方案

**方案 A（推荐，直接对齐 iOS）**：竖屏恒返回 3 列 —— 将 `columnsFor` 竖屏分支改为 `return 3;`（或把 `portraitWideBreakpoint` 下调至手机常见宽度以下，等效）。需回归其它竖屏网格页，确认 3 列不产生溢出/过窄。

**方案 B（精准，仅改受影响页）**：在切源分类相关页面给 `ResponsiveGrid` 显式传 `columns: 3`（`responsive_grid.dart:38` 已支持 `columns` 覆盖），保持其它页面不变。

> 若产品希望手机小屏仍保守 2 列，则采用方案 B；若目标是「完全对齐 iOS」，采用方案 A。

### 6.4 验收
- Android 竖屏切源分类一排显示 3 个，与 iOS 一致；无溢出/裁切。
- 横屏档位（`5-8` 列，`responsive_grid.dart:49-62`）行为不变。
